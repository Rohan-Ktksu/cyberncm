# Sandbox: run the real two-node demo with no dataset

The two-node demo normally needs a trained model and prepared windows from CIC-IDS2017, which cannot be redistributed. The **sandbox** replaces both with synthetic ones, so anyone can run the real Node A, Node B, signed directives, policy gate and userspace enforcer from a fresh clone.

```bash
pip install -r requirements.txt
cd demo/two_node
python run_sandbox.py --reset-state --autostart                    # human approval (default)
python run_sandbox.py --reset-state --autostart --autonomous-lab   # explicit bounded lab mode
```

The first run builds the synthetic data and a toy model (about 2 minutes, CPU only, a few MB under `sandbox/build/`, which is git-ignored). Then open `http://127.0.0.1:18100`. Everything on the page is labelled **SANDBOX**. After about 30 seconds the synthetic attacker `198.51.100.7` crosses the threshold and its alert waits for your approval; approving it makes the real gate block the lab client `127.0.0.2` for at most 30 seconds, while the control client `127.0.0.3` keeps working. Use **Generate report** at the bottom for a plain-language summary.

## What is real and what is synthetic

| Real (the project's own code, unchanged) | Synthetic (generated by `make_sandbox.py`) |
|---|---|
| Node A scoring loop, FP32 ONNX inference | The traffic: 32 features per 5-second window, 28,000 windows over 5 "days" |
| Ed25519 signed directives, schema checks, replay and expiry checks | Host addresses: documentation ranges only (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) |
| Node B policy gate, human approval, bounded autonomous lab mode, emergency disable | The attack families: `Portscan`, `Infiltration`, `Botnet`, `DDoS`, each a shift in a different subset of features |
| The userspace gate on one local HTTP listener, the probes, the report | The model: trained by the project's own `train.py`, `evaluate.py` and `export.py` on the synthetic windows |

## What it is not

- **It says nothing about detection quality.** The attacks are large synthetic shifts, so the toy model separates them almost perfectly. Never quote its scores as results; the research results are in `research/`.
- It is not recorded real traffic, not independent corroboration between sites, and not a validated mesh. Two processes on one machine, as in the main demo.
- The "dataset labels" shown are synthetic ground truth.

## Hosting it publicly

This is deliberately **not** offered as a hosted service. The real Node B dashboard has operator controls (start, approve, unblock, reset) and holds one shared state, so a public copy would let every visitor act on the same session. The public website instead has a static in-browser simulation. Run the sandbox locally.

## Files

- `make_sandbox.py`: generates the data and runs the build. `python make_sandbox.py [OUT_DIR] [--force]`.
- `../run_sandbox.py`: builds if needed, sets the sandbox environment variables and starts the demo.
- Environment variables set by the launcher: `CYBERNCM_SANDBOX=1`, `CYBERNCM_CHECKPOINT`, `CYBERNCM_WINDOWS`, `CYBERNCM_SUBJECT`, `CYBERNCM_PROTECTED_RECORDED`, and a separate runtime folder `runtime-sandbox/` so sandbox keys never mix with a real-data run.
- Tests: `python -m pytest demo/two_node/test_sandbox.py` (fast). `CYBERNCM_TEST_SANDBOX_BUILD=1` adds the full build.
